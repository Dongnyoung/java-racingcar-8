# Racing Car – 콘솔 레이싱 게임

간단한 규칙으로 진행되는 콘솔 레이싱 게임입니다.  
입력으로 참가자 이름과 시도 횟수를 받아 각 라운드마다 전진 여부를 판단하고, **가장 많이 전진한 참가자(들)** 을 우승자로 출력합니다.  
구조적으로는 **MVC + Service** 조합을 적용해, 입력/출력/도메인 로직을 분리하고 리팩토링 친화적으로 설계하습니다.

## 1. 설계과정

### 1) 고민

초안에서는 컨트롤러의 run()에 로직이 몰린 형태(chore 커밋).

리팩토링(SRP에 집중함)을 통해 입력/검증/등록/규칙/집계/출력 책임을 점진적으로 분리하였음.

입력값에 대해 직관적이고 철저하게 검증하는 로직을 SRP에 준수하며 작성하였음.
(입력값이 유효하다면 " : "를 기준으로 '결정한다'라는 나만의 참가자 결정기준을 두었음.)

배너 출력은 인터페이스 + Facade로 교체해서 컨트롤러의 분기/순서 책임을 제거하고.

핵심 비즈니스(전진/집계/최대/우승자)는 RaceService로 위임 → 테스트/확장 용이

### 2) 전체 흐름
- 입력 ->파싱,검증,결정 -> 시뮬레이션 시작 -> 우승자결정 -> 출력
- 컨트롤러는 오직 흐름제어와 객체 협력 조정만 담당함.

### 3) 리팩토링 단계

1) run메소드에 모든기능 구현
2) 입력,파싱,검사기 분리: InputView, InputPaser, ParticipantValidator
3) Banner 인터페이스 -> 향후 Facade패턴도입
4) 도메인 상태 분리: ParticipantRegistry
5) 도메인 정책 분리: Movement, MoveCounter, MaxMoveFinder, WinnerDecider
6) 서비스 오케스트레이션: RaceService 도입, 컨트롤러 경량화
7) 테스트 보강: 기능테스트들 시행

## 3. 적용패턴
### 1) MVC패턴
- RaceService/Domain(M) - InputView/WinnerView(V) - RacingController(C)

#### RaceService로 위임
- 초기에는 `RacingController` 내부에 입력 처리, 전진, 우승자 결정 등 여러 책임이 몰려 있어 복잡도가 높았음  
- 이를 해소하기 위해 **핵심 비즈니스 로직(전진·집계·우승자 결정 등)** 을 담당하는 `RaceService` 클래스를 별도로 작성함  
- `RaceService`는 `Movement`, `MoveCounter`, `MaxMoveFinder`, `WinnerDecider`을 **의존성으로 주입받아** 조합(Composition) 형태로 사용함  
- 컨트롤러는 더 이상 비즈니스 로직을 직접 수행하지 않고, **로직 실행을 RaceService에 위임(Delegation)** 하여 흐름만 제어함  
- 결과적으로 컨트롤러는 가볍고 테스트 가능한 구조로 리팩토링되었으며,  
  서비스 계층은 재사용성과 확장성이 높아짐

### 2) Facade패턴
- Banner에 적용

#### 왜 Facade를 적용했는가?
- 초기에 `Banner` 인터페이스로 추상화하여 각 배너(`OpeningBanner`, `TryCountBanner`, `ResultBanner`)가 `ment()` 메소드를 오버라이딩하도록 설계함  
- 그러나 컨트롤러에서 각각의 배너 인스턴스를 직접 생성하고 호출해야 해서 **의존성과 코드 복잡도**가 증가함  
- 이를 해결하기 위해 **`BannerFacade` 클래스를 도입**  
  - 컨트롤러는 Facade에게 단일 명령(`opening()`, `askTryCount()`, `result()`)만 전달  
  - Facade 내부에서 각각의 배너(Receiver)를 호출해 출력 순서와 로직을 일괄 관리  
- 결과적으로 컨트롤러는 배너의 개수나 호출 순서를 알 필요가 없어졌으며,  
  코드의 **응집도는 높이고 결합도는 낮춘 구조**로 리팩토링됨  
- 구조적으로는 Command 패턴의 “Invoker–Receiver” 구조와 유사한 흐름을 가짐

### 3) DI 지향 (Dependency Injection)
- 컨트롤러가 구체 클래스가 아닌 **역할** 에 의존하도록 설계함  
- 예를 들어 `RacingController`는 입력을 받고, 처리 후 결과를 결정하여 `RaceService`에게 전달하는 **조정자(Orchestrator)** 역할을 수행함. 
- 실제 로직 구현체의 생성과 실행은 외부(`RaceService`)에서 처리하도록 위임
- 이를 통해 **테스트 용이성**, **유연한 교체 가능성**, **낮은 결합도(Loosely Coupled)** 구조를 달성함  
- 코드 변경 없이 다른 구현체(`MockView`, `TestService` 등)를 주입해 테스트 가능

### 4) SRP & OCP (단일 책임 원칙 / 개방–폐쇄 원칙)
- 각 클래스는 **하나의 책임만 수행하도록 설계**  
  - `ParticipantValidator` → 입력 검증  
  - `ParticipantRegistry` → 참가자 등록  
  - `Movement` → 전진 규칙  
  - `MoveCounter` → 전진 횟수 집계  
  - `MaxMoveFinder` → 최댓값 계산  
  - `WinnerDecider` → 우승자 판단  
- 새로운 규칙이나 출력 형식을 추가하더라도 기존 클래스를 수정하지 않고  
  **확장만으로 기능 추가(OCP)** 가 가능  
  - 예: 전진 기준을 4→5로 바꾸거나 새로운 배너(`EndBanner`)를 추가해도  
    기존 구조는 그대로 유지됨  
- 결과적으로 유지보수성과 재사용성이 높고, 기능별 코드 파악이 용이해짐

## 회고 및 설계 의도

코드를 작성하면서 솔직히 `Car` 클래스로 구현하는 방식이 더 객체지향적으로 보일 수도 있겠다는 생각이 들었다.  
하지만 이번 구현에서는 **기능의 직관성**과 **핵심 로직의 명확한 전달**에 더 집중하였다.  
또한, 각 기능이 서로 독립적으로 확장될 수 있도록 구조를 설계하려고 노력하였다.

그래서 처음에는 **절차지향적인 접근**으로 기능을 빠르게 구현해 보고,  
그 후에 점진적으로 **리팩토링을 통해 구조를 개선**하는 방향으로 진행하였다.  

특히 `Banner`의 경우, 단순히 콘솔 출력용이 아니라  
**UI 확장 가능성**을 염두에 두어 설계했다.  
“나중에는 이 부분이 콘솔이 아닌 화면(UI)로 대체될 수도 있다”는 가능성을 생각하며  
리팩토링을 반복했고, 그 과정에서 자연스럽게 **Facade 패턴**을 적용하게 되었다.

입력값 처리 과정에서도 사용자가 입력한 문자열을 명확하게 해석하기 위해  
`InputParser`를 두고 파싱 책임을 분리하였다.  
그리고 “참가자가 확정되었다”는 의미를 주기 위해 `":"` 구분자를 사용해  
**나만의 참가자 결정 규칙**을 적용하였다.

이후 기능이 많아지고 `RacingController`에서 각 기능들을 계속 생성하고 주입하다 보니  
점점 **의존성이 커지고 부담이 증가하는 문제**가 생겼다.  
그래서 핵심 비즈니스 로직(전진, 집계, 우승자 결정 등)을 **`RaceService`로 위임**하기로 하였다.  
그 결과, 컨트롤러는 입력과 흐름 제어만 담당하고  
비즈니스 로직은 독립적으로 수행할 수 있는 구조로 리팩토링되었다.

결국 이번 프로젝트를 통해,  
“빠른 구현 → 단계적 리팩토링 → 책임 분리”의 과정을 직접 체험하면서  
**유지보수성과 확장성**을 동시에 고려하는 개발의 중요성을 배울 수 있었다.
